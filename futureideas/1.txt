A visão de longo prazo para o Agenza é evoluir de uma aplicação que gere várias sessões independentes de agentes de programação para uma verdadeira plataforma de orquestração multi-agente. Em vez de o utilizador ter de abrir vários agentes, distribuir tarefas manualmente e acompanhar individualmente o trabalho de cada um, a ideia é permitir que o utilizador fale apenas com um agente principal e lhe diga aquilo que pretende alcançar. Esse agente funcionaria como supervisor ou manager do projeto, ficando responsável por analisar o objetivo, dividir o problema em tarefas mais pequenas, criar os agentes necessários e coordenar o trabalho entre eles.

No centro do Agenza existiria um motor de orquestração responsável por gerir todo este sistema. Esse motor teria, entre outros componentes, um Agent Manager, encarregado de criar, terminar e acompanhar agentes, e um sistema de comunicação interno, semelhante a um Message Bus, que permitiria aos agentes trocar mensagens e informação entre si. Cada agente poderia ser executado através de diferentes providers ou CLIs, como Codex, Claude ou Gemini, sem que a arquitetura do Agenza estivesse dependente de um único modelo.

Cada agente seria representado internamente por uma entidade com propriedades como um identificador, nome, função, provider utilizado, estado atual, tarefa atribuída, diretório de trabalho, branch Git, permissões, contexto disponível e referência ao agente que o criou. Esta última propriedade, o parent_agent, seria particularmente importante porque permitiria criar uma estrutura hierárquica de agentes. Um Supervisor poderia, por exemplo, criar um agente de Frontend e outro de Backend. O agente de Frontend poderia posteriormente criar um agente específico para UI e outro para acessibilidade, enquanto o agente de Backend poderia criar agentes dedicados à API e à base de dados. Assim, os próprios agentes poderiam criar sub-agentes quando considerassem que uma tarefa justificava uma maior divisão do trabalho.

Esta autonomia teria, no entanto, de ser controlada. O Agenza deveria permitir definir limites como o número máximo de agentes ativos e a profundidade máxima da hierarquia. Por exemplo, poderia ser permitido um máximo de oito agentes e uma profundidade de dois níveis de sub-agentes. Desta forma, um Supervisor poderia criar um Backend Agent e este poderia criar um Database Agent, mas o Database Agent já não poderia continuar a criar novas instâncias. Isto impediria situações em que um agente criasse desnecessariamente dezenas de outros agentes para resolver tarefas relativamente simples.

Além dos limites estruturais, faria sentido introduzir um sistema de orçamento para cada execução. O utilizador poderia estabelecer limites como o número máximo de agentes, quantidade máxima de tokens consumidos, duração máxima da execução ou custo máximo permitido. Desta forma, seria possível oferecer um elevado grau de autonomia aos agentes sem perder controlo sobre os recursos utilizados. O objetivo seria que a autonomia fosse configurável e previsível, em vez de ilimitada.

Outro conceito importante seria a possibilidade de criar equipas de agentes, ou teams. O agente principal não teria obrigatoriamente de utilizar o mesmo modelo que os restantes. Uma equipa Full Stack poderia, por exemplo, utilizar Codex como Manager, Claude para Frontend, Codex para Backend, Gemini para Research e novamente Claude como Reviewer. O utilizador poderia simplesmente escolher essa equipa, escrever algo como “Build a dashboard for monitoring API usage” e o Agenza seria responsável por instanciar os agentes necessários, atribuir as respetivas funções e iniciar o fluxo de trabalho.

Estas equipas poderiam também existir sob a forma de templates reutilizáveis para diferentes tipos de tarefas. O Agenza poderia disponibilizar templates como Full Stack, Bug Fix, Code Review, Research, Refactor ou Release. Ao selecionar, por exemplo, o template Bug Fix, o sistema poderia criar automaticamente um Investigator para identificar a origem do problema, um Developer para implementar a correção, um Tester para validar o resultado e um Reviewer para analisar as alterações antes da conclusão da tarefa. O utilizador poderia ainda criar e guardar as suas próprias equipas e configurações.

A comunicação entre agentes seria uma parte fundamental desta arquitetura. Um agente de Backend poderia informar diretamente o agente de Frontend de que determinados endpoints já estão disponíveis, um agente de testes poderia comunicar ao Supervisor que encontrou uma falha e o Supervisor poderia reenviar automaticamente essa informação ao agente responsável pela área afetada. Em vez de cada agente trabalhar isoladamente, o Agenza funcionaria como a infraestrutura que permite aos agentes partilhar informação, delegar tarefas, comunicar resultados e reagir ao trabalho dos restantes.

A principal diferença relativamente a muitas ferramentas multi-agente seria precisamente o papel do utilizador. Num sistema tradicional com vários agentes, o humano continua a funcionar como orquestrador: abre cada agente, decide quem faz o quê, acompanha os resultados e transfere manualmente informação entre eles. A visão do Agenza é inverter esse modelo. O utilizador define o objetivo, comunica com um agente principal e o próprio sistema trata da execução. O Manager Agent decide quando é necessário criar outros agentes, distribui o trabalho, acompanha o progresso, resolve dependências e coordena sub-agentes até que o objetivo esteja concluído.
